# Приемен тест от собственика — Before I Deploy 11.0.0-rc.1 (български)

Цел: да провериш кандидата от първото стартиране до първия release, мониторинг и покупка в тестов режим —
на реален Mac, с реален Netlify тестов сайт, реален Supabase проект и Paddle **sandbox**. Нищо тук не пипа
production сайт на клиент и не прави реална покупка.

Отбелязвай всеки ред с ✅ / ❌ и запиши какво видя. Ако нещо не съвпада с описаното, това е блокер за
публично пускане, не „дребно“.

## 0. Подготовка (веднъж, ~30 мин)

- [ ] Mac с macOS 13+, чист потребителски профил (или нов потребител) **без** инсталиран Node.js — това
      доказва, че вграденият runtime работи.
- [ ] `git pull` на клон `claude/nifty-edison-1195gi`, commit `<виж RELEASE-CANDIDATE-AUDIT.md>`.
- [ ] Supabase: изпълни `supabase/schema.sql` в SQL Editor (може да се изпълнява повторно); качи функциите:
      `supabase functions deploy admin ai-fix account`, `supabase functions deploy billing --no-verify-jwt`,
      `supabase functions deploy monitor --no-verify-jwt`; задай тайните: `ANTHROPIC_API_KEY`,
      `PADDLE_API_KEY`, `PADDLE_WEBHOOK_SECRET`, `PADDLE_ENV=sandbox`, `MONITOR_CRON_SECRET=<дълъг случаен низ>`.
- [ ] Изпълни `supabase/monitor-cron.sql` (замени двата placeholder-а). След 5–10 мин:
      `select * from monitor_heartbeat order by at desc limit 3;` трябва да връща редове.
- [ ] Paddle sandbox: продукти/цени за Flash, High, Knight и двата пакета; price id-тата в
      `settings.billing.catalog` (Admin панел); webhook destination към `<SUPABASE_URL>/functions/v1/billing`.
- [ ] Netlify: тестов сайт (напр. `bid-acceptance.netlify.app`), свързан с тестов проект-папка (статичен
      `index.html` е достатъчен), `netlify login` направен на Mac-а.
- [ ] Build: `zsh scripts/bundle-node.sh && zsh Rebuild.command` (или `zsh scripts/release.sh --allow-dev
      --skip-notarize` за DMG без подпис). Без Developer ID сертификат билдът е **unsigned** — Gatekeeper ще
      поиска „Отвори въпреки това“; това е известен блокер за публично пускане (виж §9).

## 1. Инсталация и първо стартиране

- [ ] Копирай `Before I Deploy.app` в /Applications и стартирай. Приложението тръгва без Node на машината
      (`bid doctor` в Settings → Engine показва `runtime: bundled`).
- [ ] Welcome екранът показва стъпките: акаунт или локален режим → добавяне на проект → свързване на hosting →
      първа проверка → AI предложение → preview → мониторинг. Текстовете са на български при системен език BG.
- [ ] Смени езика на EN и обратно (Settings → Language) — всички нови екрани (AI асистент, План и използване,
      Мониторинг) се превключват без „сурови“ ключове.
- [ ] Светла и тъмна тема: Settings → Appearance; прозорецът на 1100×700 и на цял екран — няма отрязани текстове
      с дълги български низове.
- [ ] VoiceOver (⌘F5): навигационните редове, бутоните на асистента и лентата за използване се четат с етикети.

## 2. Акаунт и локален режим

- [ ] Регистрирай нов акаунт (имейл + парола). Първият акаунт става admin.
- [ ] Излез и провери, че приложението работи в локален режим: проверка на проект без AI и без облак.
- [ ] Влез отново. Settings → Account показва плана **Free**.

## 3. Добавяне на сайт и проверка

- [ ] Добави тестовата папка. Проверката минава; проблемите се появяват в „Проблеми“ с тежест, вид, доказателство.
- [ ] Създай `.env` в папката и я добави в git (`git add .env`). Нова проверка → блокер „.env в Git“ със safe
      fix. Приложи го → „Проверено“ (зелено) и `.env` е извън Git. Върни го назад през Undo, ако има.

## 4. AI асистент (реален модел)

- [ ] Без план: асистентът обяснява, че AI изисква план или собствен ключ; нищо не се изпраща.
- [ ] Settings → AI → добави собствен Anthropic ключ **или** стартирай пробния период (§7). Съгласието за
      изпращане на данни се показва веднъж.
- [ ] Счупи `src/app.js` (или `index.html` със синтактична грешка, ако проверката я хваща) → „Обясни проблема“:
      панелът вдясно показва **какво ще бъде изпратено** (проблем, лог, файлове, маскирани тайни) и оценка в
      токени; отговорът е структуриран (статус, наблюдения с E-id, хипотези, следващи стъпки).
- [ ] „Предложи поправка“ → diff, риск, план за проверка; файлът на диска **не** е променен.
- [ ] „Приложи и провери“ → етапите Предложение → Прилагане → Проверка; накрая „Проверено“ или „Непроверено“
      с реален статус. Undo връща файла.
- [ ] Сложи фалшив ключ във файл (`const KEY = 'sk-ant-api03-xxxxxxxxxxxxxxxxxxxx'`) и го избери във
      „Файлове“ → в списъка „Какво ще бъде изпратено“ има иконка с маскиране (≥ 1); ключът не се вижда в отговора.
- [ ] Натисни „Спри“ по време на отговор → редът показва „Спряно от теб. Нищо не е променено.“
- [ ] „Готовност за пускане“ при блокирана проверка → отговорът повтаря `blocked`; не предлага deploy.
- [ ] Реалният разход след операцията се вижда в реда и в „План и използване“ (история на операциите).

## 5. Release поток (Netlify)

- [ ] Свържи hosting (Netlify) към тестовия сайт. Dashboard показва capability матрицата.
- [ ] „Release…“ → проверка → preview → smoke → чака DEPLOY. Отвори preview линка.
- [ ] Промени `index.html` **преди** да натиснеш DEPLOY → promote отказва (stale), нищо не е публикувано.
- [ ] Ново preview → въведи DEPLOY → публикува същия deploy id → проверка на production → „succeeded“;
      Deployments card маркира публикувания deploy.
- [ ] Натисни DEPLOY два пъти бързо (или повтори promote от CLI) → един publish, не два.
- [ ] „Rollback…“ → въведи ROLLBACK → предишният deploy е публикуван и проверен; текстът казва, че се връщат
      само файлове.
- [ ] Затвори приложението по средата на promote (`kill` на процеса) → при следващо отваряне операцията е
      `interrupted`, статусът е верен спрямо Netlify.

## 6. Мониторинг

- [ ] Monitoring card: „Върви на този Mac…“; включи фоновия агент (иска потвърждение).
- [ ] Включи „Облак“ за сайта → регистрира се live URL-ът; статусът показва scheduler „жив“, последно/следващо
      изпълнение, 90 дни история. Ако cron не е насрочен — картата казва „никога не е работил“, не зелено.
- [ ] Спри Netlify сайта (Site settings → Deploys → unpublish / или смени на 404 деploy) → след 2 цикъла в облака
      има инцидент с източник „облак“; на Mac-а — с източник „този Mac“; без дублиране на един и същ проблем.
- [ ] Приспи Mac-а за 15 мин с изключено приложение → в облака има нови probe-и (`monitor_probes`), инцидентът
      продължава; при връщане на сайта — „recovered“.
- [ ] Добави webhook (напр. Slack incoming webhook, https) → „Изпрати тест“ пристига в канала; при потвърден
      инцидент и при възстановяване — по едно съобщение, без повторения за „ongoing“.
- [ ] Прозорец за поддръжка (CLI: `bid monitor maintenance add --from … --to …`) → пробите са „непроверено:
      поддръжка“, няма известия.

## 7. План, кредити, покупка (Paddle sandbox)

- [ ] „План и използване“: Free, календарен период, 0 включени токена, история празна.
- [ ] Стартирай пробния период → High, 150 000 токена, крайна дата; втори опит е отказан.
- [ ] Купи пакет 500k с тестова карта (Paddle sandbox 4242…) → след webhook балансът „Купени пакети“ расте;
      redirect-ът сам по себе си не променя нищо (провери преди webhook-а).
- [ ] Откажи checkout → нищо не се променя. Отказана карта → нищо не се променя.
- [ ] Абонирай се за Flash (месечно) → планът и периодът идват от Paddle; „Manage subscription“ отваря портала;
      смени на High от портала → след webhook планът е High; „Синхронизирай с доставчика“ дава същия резултат.
- [ ] Изчерпай дневния таван (или намали `ai.dailyCapPercent` от Admin) → AI отказва с ясен текст; проектът,
      историята и rollback остават достъпни.
- [ ] Просрочено плащане (Paddle sandbox → simulate past_due) → статус „просрочено плащане“, планът остава 3 дни.
- [ ] Възстановяване (refund от Paddle dashboard) → ред `refund` в историята, балансът намалява.

## 8. Клиентска изолация (Supabase)

- [ ] Втори акаунт (друг имейл) не вижда проекти, инциденти, кредити или история на първия (провери през
      приложението и през `select` с anon key + JWT на втория).
- [ ] `tests/rls` минава на CI (виж RELEASE-CANDIDATE-AUDIT.md).

## 9. Инсталация/деинсталация и подпис

- [ ] Ъпдейт: качи `latest.json` с по-нова версия → банерът се показва; изтеглянето проверява sha256.
- [ ] `zsh scripts/uninstall.sh --all` маха приложението, engine-а, агента, настройките и ключовете от Keychain.
- [ ] Подпис/нотаризация: с Developer ID и notary профил `zsh scripts/release.sh` дава DMG, който Gatekeeper
      приема без предупреждение. **Без тях кандидатът е unsigned и не е готов за публично пускане.**
