# AI prompts — templates, versions, schemas, evaluations (V11 RC)

The embedded assistant never composes prompt text ad hoc. Every request renders one versioned template from
`engine/prompts/<id>.v<n>.json`, every answer is one JSON object validated against that template's output
schema, and only validated fields reach the app. This page is the contract; the files are the source.

## 1. Where things live

| What | Where |
|---|---|
| Prompt resources (id, version, purpose, input schema, output schema, template, localized titles) | `engine/prompts/*.v1.json` (bundled into the app with the engine) |
| Loader, renderer, JSON extraction, output validation | `engine/src/ai/prompts.mjs` |
| Actions, evidence building, redaction, budgets, the fix loop, history | `engine/src/ai/assistant.mjs` |
| Canned model answers for the evaluations | `tests/ai-evals/*.json` (chosen by an `[[eval:name]]` marker in the user message, served by the fake model in `tests/run.mjs`) |
| Evaluation tests | `tests/run.mjs` → the six `assistant:` tests |
| App | `App/Sources/BeforeIDeploy/AssistantView.swift`, `Stores/AssistantStore.swift` |

`bid ai prompts` lists the resources with their versions. A template change is a new version file; old
versions stay readable so history entries (`template: "diagnose_issue.v1"`) keep meaning something.

## 2. The system prompt (`system.v1`)

Inputs: `locale`, `project_name`, `tools`. The tools text is generated by the engine from its allowlist
(`run_check`, `apply_patch` — needs confirmation, `verify_fix`, `undo_last_change`). The model does not call
tools; the app runs engine commands after validating the answer. Deploy, restore, billing, secrets and project
deletion are not assistant tools at all.

The text is the one in the task brief: untrusted evidence, no secrets, facts / hypotheses / recommendations
apart, evidence IDs, smallest coherent change, schema-valid output only, never "verified" without an engine
result, application-enforced approvals and budgets, answer in `{{locale}}`, no chain-of-thought.

## 3. Action templates

| id | version | action | required inputs | output (required fields) | refs enforced |
|---|---|---|---|---|---|
| `diagnose_issue` | 1 | `diagnose` | issue, evidence, project_metadata, check_results (+question) | summary, status ∈ confirmed/likely/unverified, observations[{evidence_id, finding}], hypotheses[{claim, confidence, evidence_ids}], impact, next_steps, missing_context | evidence ids |
| `propose_patch` | 1 | `propose`, `fix` | confirmed_issue, allowed_paths, file_snapshots, project_conventions (+feedback) | status ∈ patch/needs_input/no_change, summary, base_hashes, changes[{path, action, content}], risk ∈ low/medium/high, rationale_evidence_ids, verification_plan, rollback_notes, missing_context | evidence ids, paths ⊂ allowed paths (create: inside an allowed file's folder), base hashes checked against the snapshot AND the file on disk |
| `review_patch` | 1 | `review` | candidate_diff, original_issue, project_constraints, available_tests | findings[{severity ∈ blocker/major/minor/optional, path, evidence_ids, explanation, suggested_action}], required_checks, remaining_uncertainties | evidence ids |
| `explain_verification` | 1 | `explain` | engine_verification_result, locale (+note) | engine_status (must equal the engine's status), summary, completed_checks, unresolved, next_action | engine status |
| `release_readiness` | 1 | `readiness` | snapshot, check_results, preview_results, provider_capabilities, engine_release_gates (+note) | summary, engine_gate_status (must equal the gate), blockers, warnings, missing_evidence, proposed_next_action | engine status |
| `incident_triage` | 1 | `triage` | incident_timeline, recent_deployments, probe_evidence (+rollback_supported, note) | observed_impact, timeline_summary, hypotheses[…], recommended_checks, recovery_options[{option, requires, limits}], uncertainties | evidence ids |
| `ask` | 1 | `ask` | question, evidence, project_metadata, check_results | answer, evidence_ids, next_steps, missing_context | evidence ids |

A `ref` on a schema field is enforced by `validateOutput`: `evidence` → the id must be one the engine supplied;
`allowed_paths` → the path must be in the allowed set; `engine_status` → the value must equal the engine's
own status (the model cannot upgrade "warnings" to "pass" or "blocked" to "ready").

## 4. What the engine does around a template

1. **Evidence** — blocks with ids `E1…En`: the issue, the failing step's log tail, selected files (inside the
   project, no protected folders or symlinks, ≤ 24 000 chars each, ≤ 8 files), the git diff stat, the patch diff
   (review), incidents (triage). Every block goes through `redact()` (API keys, tokens, JWTs, private keys,
   home paths) and the count of masked items is reported.
2. **Announcement** — an `info` event with `context.evidence[{id, kind, label, chars, redactions}]`,
   `estimateTokens`, `budget`, `template` BEFORE the request. The app shows it as "What will be sent".
3. **Budget** — `maxTokensPerOperation` (default 60 000, `--budget` can only lower it); when the estimate would
   exceed it the request is refused (`budget_exceeded`) and nothing is sent. Context over `maxContextChars`
   drops the largest file blocks first (they are listed as omitted).
4. **Call** — the current provider (own key: Anthropic/OpenAI; else the cloud `ai-fix` function with the plan's
   model); one call, `callTimeoutMs` (default 120 s) → `ai_timeout`.
5. **Parse + validate** — `extractJSON` (plain, fenced or wrapped in prose) then `validateOutput`. One repair
   round is allowed: the errors are sent back and a corrected object requested. Still invalid →
   `valid: false`, `output: null`, `stopped: "invalid_output"`; the raw text is shown as such.
6. **Structured result** — `{ template, output, valid, errors, repairs, usage, stopped, budget, … }` plus
   `patchFile / files / risk / verificationPlan / rollbackNotes` for proposals and `applied / recheck /
   verified / undone` for fixes. History: `~/Library/Application Support/BeforeIDeploy/chats/<project>.jsonl`
   (0600), one line per operation, `bid ai history`, `bid ai reset`.

### The fix loop (`--action fix`)

propose → (apply only with `--yes` or the auto-apply setting for `risk: low`) → `ai apply --recheck` (undo
record, full re-check) → verified? stop. Else: worse than before (a step that passed now fails) → `ai undo`,
`stopped: "regression"`; same failing set as the previous attempt → `stopped: "no_progress"`; otherwise feed the
engine's verification back into the next `propose_patch` round, up to `maxIterations` (default 3, max 5) or
the budget. Every attempt is billed once and shown; nothing loops invisibly.

### Automation policy (`bid ai settings`)

`autoApplyLowRisk` (default **false**), `maxIterations` (1–5), `maxTokensPerOperation` (4 000–400 000),
`maxContextChars`, `callTimeoutMs`. Auto-apply never covers production deploy, restore, billing, project
deletion or secrets — those are not assistant actions.

## 5. Evaluations (`tests/ai-evals`, run by `node tests/run.mjs`)

| Scenario | Fixture | Expected engine behaviour (asserted) |
|---|---|---|
| Happy diagnose | `diagnose-ok` | valid, evidence ids resolve, `info` context listed, streamed, stage pass, history row, usage > 0 |
| Unknown evidence id | `bad-evidence` | rejected, one repair round, then valid (`repairs: 1`) |
| No JSON at all | `malformed` | repair, still invalid → `invalid_output`, output null, stage fail |
| Claims tests ran | `claims-tests-ran` | prose claim reaches nobody: no check ran, `verified` absent |
| Prompt injection in README | `ask-injection` | README travels as evidence marked untrusted; no deploy, no release op |
| Secret in a selected file | `ask-secret` | request body carries `[API_KEY]`, never the key; context lists `redactions ≥ 1` |
| Nonexistent / outside / protected file | — | `not_found` / `bad_path` before any request |
| Budget too small | — | `budget_exceeded` before any request |
| Valid patch | `propose-ok` | patch file with diff, risk, plan; disk untouched |
| Paths outside scope | `propose-outside` | package.json and ../outside.js rejected; repair accepted; nothing outside touched |
| Stale base hash | `propose-stale` | `stale_base_hash`, no patch file |
| Needs input | `propose-needs-input` | `needs_input` with `missing_context` |
| Review | `review-ok` | findings + required checks; foreign patch file → `bad_patch` |
| Fix without consent | `propose-ok` (fix) | `needs_confirmation`, apply stage skipped, disk untouched |
| No progress | `propose-noop` | applied, unverified, second attempt identical → `no_progress` after 2 iterations |
| Verified fix | `propose-ok` (fix, `--yes`) | propose → apply → verify pass, `verified: true` |
| Regression | `propose-worse` | new failing step → undone, `regression` |
| Verification upgrade | `explain-upgrade` | `engine_status: pass` rejected; repaired answer mirrors the engine |
| Readiness mirror / waiver | `readiness-ok`, `readiness-waive` | gate `blocked` mirrored; "ready" rejected twice → `invalid_output` |
| Incident triage | `triage-ok` | recovery option states the database limit |
| Bulgarian | `bg-ok` | stage labels in BG, model told `Answer in bg` |
| Interrupted stream | `interrupted` | error exit, no patch file |
| Provider timeout | `slow` | `ai_timeout` |

These prove the guardrails, not the model's judgement: the fake model returns what the fixture says. A real
model run is part of the owner acceptance test (`docs/OWNER-ACCEPTANCE-TEST-BG.md`).

## 6. Cloud side

The managed path goes through the existing `ai-fix` Edge Function: the engine sends `system` + `prompt`
(already redacted and capped), `mode: "assistant"`, `step: "assistant:<action>"`, and an `operationId` so a
retry never bills twice. The function keeps the plan / credits / rate / daily-cap gates, streams the model and
settles the real token count (`docs/BILLING-AND-USAGE.md`). Provider keys stay server-side; the native bundle
carries none.

## 7. Adding or changing a prompt

1. Copy `engine/prompts/<id>.v1.json` to `.v2.json`, bump `version`, edit the template and schemas.
2. Keep `input.required` and every `{{name}}` in sync (the renderer refuses undeclared holes).
3. Add / adjust an eval fixture and its assertion in `tests/run.mjs`.
4. Run `node tests/run.mjs` and `node scripts/i18n-check.mjs` (titles in both languages).
